## 3. 最有价值的工程难题：自愈型缓存 bug

- **起因**【实测】：注册成功后立即登录返回 401，约 1 分钟后自愈；冒烟日志两次复现（23:11:00 注册 → 0.1s 内登录 401）。
- **排查路径**【实测】：Redis 中发现 `cache:user:phone:{13800138000 true}` 键 → 怀疑 go-zero 占位缓存 → **源码取证闭环**：`cachenode.go` 的 `doTake` 在 DB 查不到时写入 `"*"` 占位符；`cacheopt.go` 的 `defaultNotFoundExpiry = time.Minute` 解释了自愈窗口。
- **根因**【实测】：注册查重走 `FindOneByPhone`（未命中 → 写占位），而插入走 `TxInsert` 事务 session，**绕过了 goctl 生成代码** `Insert` **自带的** `ExecCtx` **缓存清理** → 占位残留 → 立即登录命中占位直接返回 `ErrNotFound`。
- **修复**：自定义层新增 `DeleteCache`（与生成代码同一套 key 规则，删主键/手机/邮箱三 key），注册事务提交后调用，失败仅记日志不回滚【实测：修复后 captcha→register→立即 login 全 200，Redis 键值从 `*` 变为真实主键】。

## 4. 通用规律（可迁移）

1. **跨 Model 事务必然绕过单 Model 的缓存维护**——事务提交后必须显式失效相关 key，这是 go-zero（乃至一切“生成代码自带缓存维护”框架）的隐藏义务。
2. **“TTL 窗口后自愈”是占位/限流类 bug 的指纹**：遇到“过几分钟就好了”的问题，先查缓存占位与限流，别急着复现重试。
3. **生成区/修改区边界要可验证**：用同版本、同 style 的 goctl 生成纯基线做逐字节 diff（本次审计结论：生成区零污染，修改全部在可编辑层）——把“生成后只改 logic”从口号变成事实。
4. 评审的价值顺序：**契约闭合（DR-2）> 权限（DR-3）> 风险显式化（DR-4）**，架构方向（双 Token、一致性哈希）反而无需推翻【评审判断，复盘认可】。

## 5. 成长判断

这次比原来多出的两项可独立完成的判断：

1. **能独立定位“自愈型”缓存 bug**：从症状（TTL 窗口）反推机制（占位缓存），用 Redis 键值 + 框架源码 + 冒烟日志三重证据闭环，而不是靠重试绕过。
2. **能独立审计 AI 生成代码的规范边界**：用 goctl 纯基线 diff 证明哪些是生成、哪些是修改，使「先写 api/sql → 生成 → 在生成之上修改」成为可验收的流程而非信任。
