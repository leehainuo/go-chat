## 1. 双 Token 会话体系：从"不闭环"到"闭环" ✅

**难点**：设计卡写了不变量 3"同一 userID 任意时刻最多一个有效 refreshToken"，但没有写机制。评审用一条攻击路径证伪了它：设备 2 登录踢掉设备 1 时只删了 `user:refresh:{userID}`，没删 `refresh_token:{旧rt}`——设备 1 拿旧 rt 仍能续签成功，单点登录失效。

**最终方案**（`service/user/api/internal/service/token_service.go` 已落地）：

- 踢号时先读旧 `user:refresh:{userID}` 的值，**补删 `refresh_token:{旧rt}`**（`IssueTokens`）；
- 续签做**双重校验**：`refresh_token:{rt}` 存在，且该 rt 必须等于 `user:refresh:{userID}` 的当前值，被踢或已轮换的旧 rt 直接 401（`RefreshTokens`）；
- 续签轮换 rt，并发续签的竞态用"后写者覆盖 user:refresh、先写者下次续签被第 2 步拒绝"自然收敛，最终仍保持单点（代码注释已写明该推理）；
- `Logout` / `KickRefresh` 同步删三把 key；改密后已签发 accessToken 保留至自然过期（≤30min）是设计卡 §4 预先声明的接受风险。

**面试一句话**：单 Token 无法踢人和无感续签；双 Token 的关键不在两个 Token，而在**服务端状态机闭合**——任何路径（新登录、改密、登出、轮换）都必须同时维护三把 Redis key 的一致性，否则不变量只是纸面声明。

**追问预判**：为什么 accessToken 泄漏窗口可接受？→ 30 分钟 TTL + 白名单存在性校验提供踢号即时性；改密场景明确接受最长 30 分钟残留窗口（👤 设计卡 §4"我最担心的失败方式"，代码注释已引用）。

**初版取舍回顾**（👤 设计卡推理）：accessToken 短 TTL 缩小泄漏窗口 + refreshToken 实现无感续签和自动踢号；备选的单 Token 方案被否，因为泄漏后既无法踢下线也无法续签。WS 节点分配用一致性哈希而非固定取模，避免扩缩容时大量连接打散重连；环为空时留空不阻断登录（`token_service.go` 降级注释）。

## 2. 错误处理体系：个人偏好让位于公共契约 ✅

**分歧**：设计卡初版写"错误码统一 net/http + 严禁 panic"，评审指出这与需求文档已建成的 `ErrorCode(40xxx/70xxx) + Throw panic + Recover 中间件` 体系直接冲突——选 net/http 会破坏前端契约（验收标准第一条就是 `{"code":40000,...}`），且成为后续 8 个模块中的唯一例外。

**结论**：回归公共体系。

**可迁移原则**：框架级约定（错误码、响应包、panic 策略）是**跨模块契约**，单个模块无权另起炉灶；"严禁 panic"是 Go 社区正确理念，但 panic+Recover 集中转 JSON 是等价的工程实现，理念要服务于契约一致性。

## 3. go-zero 的"假事务"陷阱 ✅

**难点**：设计卡写"事务使用 go-zero 自带的 sqlx 事务能力"——但 go-zero Model 层每次方法调用独立取连接，直接调 `Insert()` 各自提交，**根本不在同一事务里**。

**最终方案**（`register_logic.go:96-115` 已落地）：`TransactCtx` 把 `sqlx.Session` 放进 context，所有 model 方法提供 `Tx` 前缀变体（`TxInsert`）从 session 执行。注册三表写入（user + user_balance + balance_log）要么全成要么全滚。

**面试一句话**：框架封装的事务能力要看清"连接"粒度——跨 Model 事务的通用解法是把事务对象注入 context 传递。这套 Tx 前缀模式后来直接复用到 phase-02 的五行写入（`AddFriendTx`），基础设施先行降低了后续"改主意"的成本。

## 4. 并发注册：唯一索引兜底 + 错误语义 ✅

**方案**：兜底靠数据库唯一索引（`uk_phone` / `uk_email`），应用层不做查后插。评审补了关键一刀：并发冲突时 MySQL 返回 duplicate key error，直接透传会变成 500。

**落地**（`register_logic.go:117-121`）：捕获 `Error 1062` 映射为 `409 Conflict("账号已被注册")`。

**面试一句话**：唯一索引是并发安全的最终防线，但**错误码映射**决定对外语义——1062 是业务可预期冲突，不是系统错误。⚠️ 评审定义的"10 并发注册仅 1 条成功且返回 409"用例未自动化，待核实。

## 可迁移原则（换项目仍然成立）

1. **不变量必须配机制**。"同一账号最多一个有效 refreshToken"写一百遍，不如"续签时校验 rt == user:refresh 当前值 + 踢号补删旧 rt"这两行实现。设计卡里每条不变量都要能回答"靠什么保证"。
2. **契约一致性优先于局部理念**。单模块的错误处理风格再"正确"，也不能破坏全局响应契约。
3. **跨 Model 事务的通用解法是事务对象随 context 传递**，与具体框架无关。
4. **区分"没意识到"与"主动接受"**——已接受风险要写进设计卡风险行，否则评审与复盘无法区分两者。
