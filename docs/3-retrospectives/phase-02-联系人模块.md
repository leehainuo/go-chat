## 1. 好友表：单行 Hash 方案被推翻——本次最有价值的设计分歧 ✅

**初版推理**（👤 设计卡原话）：两 userID 比较大小后存同一列，理由是"减少内存占用、强关联无孤立数据、天然保证状态一致性"。这是真实流行过的 pair-row 业界方案，不是拍脑袋。

**为什么被推翻**（评审 DR-1，三条硬伤）：

1. **单向拉黑无法表达**。微信语义是 A 拉黑 B 后 B 无感知（A 行 Blocked、B 行仍 Normal）。单行只有一份 status，A 拉黑 B 会让 B 的好友列表也把 A 显示成拉黑；且阶段 4 消息校验缓存 `msg:validate:friend:status:{a}:{b}` 按**方向**取 key，单向语义被破坏——这是跨阶段契约级冲突，不是实现细节。
2. **查询退化**。好友列表变成 `WHERE user_a = me OR user_b = me`，OR 条件让两个单列索引都难以命中。
3. **生态成本**。需求文档全部 model 方法（`DeleteByBothDirectionsTx`、`UpdateStatusByUserIdFriendId` + 行级归属校验）按两行写，单行方案一个都落不了地。

**反过来看"优势"为什么不成立**：省一行存储（好友关系量级下可忽略）；"天然一致性"在两行方案里由事务插两行同样成立，不构成单行独占优势。

**最终选择**（👤 + 已落地）：

- friend 表两行双向，`UNIQUE (user_id, friend_id)` + 反向索引 `idx_friend_user(friend_id, user_id)`（`deploy/sql/gochat.sql`，DDL 注释记录决策理由）；
- `AddFriendTx` 在外层事务内插 5 行：session + 2×user_session + 2×friend（`friend_service.go:162`）；
- `BlockFriend` 只改归属行，幂等——已是拉黑态直接成功（`friend_service.go:252`）。

**选择理由**（👤）：两行是**零改造成本**——需求文档、课件、阶段 4 缓存契约全部按两行写；而"事务插两行"的代价因 phase-01 的 TransactCtx 模式现成，几乎为零。

**面试一句话**：评估数据模型不只看存储和写入，要看它**能否表达产品语义（单向拉黑）**、**查询路径是否退化（OR 索引失效）**、以及**与上下游既有契约的兼容成本**。"省一行"是最不重要的那条维度。

**追问预判**：什么时候 pair-row 方案是合理的？→ 双方行为严格对称、无需表达单向状态、且查询天然按"整对"检索时（如某些配对关系表）；本项目的拉黑/删除恰好都是单向归属语义，所以不适用。

**这是复盘里最值得讲的故事**：初版推理有真实依据 → 被具体反例证伪 → 推翻的代价因复用已有事务基础设施趋近于零。面试官问"你做过什么被推翻的设计"，这就是素材。

## 2. 删除好友：物理删 vs 软删——纯粹的产品取舍 ✅

**难点**：设计卡内部三处矛盾（验收写"软删除"、流程写"修改字段"、需求文档 4.6 是物理 DELETE 四处），实现时无法判断听谁的。评审指出两种语义产品行为完全不同：物理删把单聊会话一起删掉（聊天记录入口消失），软删保留但引出"删除后对方还在会话列表"的新产品问题。

**最终选择**（👤 + 已落地）：**物理删**——事务内清 apply_friend（双向）、friend（双向）、user_session、session 四处；提交后清 model 缓存与阶段 4 好友状态缓存（`DeleteFriend`，`friend_service.go:203-249`）。

**理由**：阶段 4/5 消息校验按"删除后会话不存在"设计，物理删与后续阶段自洽；软删要重写需求文档 4.6 且引入范围外产品问题。复刻语境下选改动面小的。

**细节处置**：`Deleted=2` 保留常量但 DDL 注释明确"物理删除方案下无写入路径"；`status != 2` 过滤留作防御条件。事务外读会话、事务内再删的顺序有注释论证（删除路径上会话只减不增，并发新建会话需走"通过申请"，而申请行在同一事务内被删，天然互斥）。

**面试一句话**：这不是技术优劣题——物理删的代价是**产品妥协（删除后聊天记录入口消失）**，软删的代价是**需求重写**。取舍本身可以，但必须显式写进风险行，让评审能区分"没意识到"与"主动接受"。

## 3. 幂等与并发：不变量必须有机制，顺带修了课件一个 bug ✅

**难点**：设计卡不变量 1、2 只写了"要保护"，没写"靠什么保护"。评审构造了两个具体竞态：并发两次发申请同时通过"无待处理申请"检查 → 双插两行；两个并发 accept 都通过内存校验 → 好友关系重复行。

**最终方案**（三层防御，均已落地）：

1. `apply_friend` 表 `UNIQUE (sender_id, receiver_id)` 兜底并发双插（`deploy/sql/gochat.sql`）；
2. accept 用**条件更新**（数据库层 CAS）：`UPDATE ... WHERE apply_friend_id=? AND status IN (0,3)`，`RowsAffected==1` 才继续 `AddFriendTx`，全程事务内（`TxUpdateStatusById`，`apply_friend_model.go:25-27,92`，接口注释写明"RowsAffected==0 表示状态已被并发修改"）；
3. `user_session` 表 `UNIQUE (session_id, user_id)` 终极兜底。

**额外收获**（👤 本人发现）：课件 `SendFriendRequest` 只在 status ∈ {Unread, Read} 时复用行，Rejected/Expired 后走 Insert → 撞唯一键 → 返回 SystemError（系统错误）。修复规则改成"**存在申请行即复用**"（UPDATE 回 Unread + 新留言 + 新时间）：既支持微信式"被拒后重新申请"，又消掉撞键崩溃；Accepted 的行走不到该路径——前面"已是好友"已拦截，配合物理删也无残留行。

**面试一句话**：并发正确性分三层——**唯一索引兜底**（最后防线）、**条件更新 CAS**（把业务判断原子化，不依赖先查后改）、**事务包裹**（多表一致）。先查再改的内存判断在并发下永远不成立。该模式可直接迁移到秒杀、库存扣减、唯一审批流。

## 4. 事务与 Kafka 通知的顺序 ✅

**难点**：先发通知后提交 → 事务回滚产生"幽灵通知"（对端看到申请通过但点进去无会话）；提交后发送 → Kafka 失败对端永远无感知，过期事件丢失则申请永不过期。

**最终选择**（👤 + `notifier.go` 已落地）：

- **事务提交成功后发送，失败仅记 Error 日志，绝不影响业务结果**（`ContactNotifier` 接口注释直接引用 DR-5 决策）；
- Kafka 未配置 Brokers 时降级为 `nopNotifier` 仅日志，保持调用方逻辑不变；
- 过期事件挂 `friend-request-creation-topic`，消费端归属 phase-07 红包过期调度器（Redis ZSet 延迟队列），并规划"SQL 扫表（status IN (0,3) AND 超时 → Expired）"作不依赖 Kafka 的保底；
- 已知代价：24h 过期可能延迟生效，无实际危害，风险可接受（👤）。

**面试一句话**：消息与事务的一致性光谱是"发后滚（幽灵消息）→ 滚后发（可能丢通知）→ Outbox（最终一致但复杂）"。按业务容忍度选位置：通知类业务选滚后发 + 尽力而为，资金类必须 Outbox 或本地消息表。能说出这个光谱本身就是加分项。

## 5. 搜索语义：唯一列上的"模糊列表"是伪需求 ✅

**问题**：设计卡初版写"右模糊查询返回匹配的联系人列表"。评审指出：手机/邮箱是**唯一列**，右模糊最多命中 1 条，"返回列表"这个语义本身不成立；需求文档与课件实际是正则分派后精确等值查询单条。

**最终方案**（已落地）：`SearchUser` 正则分派（`consts.IsPhone` / `IsEmail`）+ 等值查询 + 单条返回，关键字不匹配正则直接 ParamError（`friend_service.go:37`，注释引用 DR-6）。真正的"模糊搜人"（昵称模糊）是另一个功能——不同索引设计、更大隐私暴露面，将来单独立项。

**附带决策**（👤）：越权防护保留 `:userID` 路径参数 + 逐接口比对（`mustUserId(ctx)` + 不等返回 Forbidden），理由是与 phase-01 已上线契约一致、URL 形状与课件前端兼容；删路径参数是更干净的终态但不值得在本期推翻已上线契约。好友列表同时把课件的 N+1 查询改为批量查（`GetFriends`：一次查关系 → `FindByUserIds` 批量 → 一次 JOIN 查会话 → 内存过滤分页），记为已知优化。

**面试一句话**：接口语义错误比实现错误更贵。"手机号模糊搜索"是需求评审阶段就该砍掉的伪需求——数据特性（唯一性）决定了它天然是精确查询。

## 可迁移原则（换项目仍然成立）

1. **数据模型先验语义表达能力，再谈存储效率**。能否表达产品的方向性行为（单向拉黑）是第一性问题；"省一行"是最不重要的维度。
2. **与已有契约的兼容成本是方案取舍的一等公民**。方案永远在具体系统语境里评估：单行方案在真空里未必输，但要重写需求、破坏跨阶段缓存契约时就输了。
3. **不变量必须配机制**：唯一索引兜底 + 条件更新 CAS + 事务包裹，三层缺一不可；"需要并发保护"没有机制等于没写。
4. **消息与事务的一致性按业务容忍度在光谱上选位**，并把最坏情况（通知晚到/不达）显式写进设计卡，而不是默认引入 Outbox。
5. **接口语义在需求阶段就要用数据特性校验**（唯一列 → 精确查询），语义级返工比实现级返工贵得多。
6. **基础设施先行复利**：phase-01 的 TransactCtx 模式让本次推翻重设计的代价趋近于零——好的基础设施降低的是"改主意"的成本。
