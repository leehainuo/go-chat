## ② 方案复述

目标：user-api 完成账号体系全链路（验证码→注册→登录→双 Token 续签→登出）+ 资料/头像 + 余额查询。四个不变量（账号唯一、注册同事务、单点 refreshToken、分存储）与双 Token、一致性哈希两个核心取舍均来自需求文档，方向正确。验收场景覆盖了注册、登录踢号、改密码、头像直传四条主线，**无遗漏关键场景**。

## ③ 结论：有条件通过

骨架合理，但有 2 个阻塞项需先落实，5 个决策需作者回应。

### 关键问题

**DR-1｜阻塞｜权限/失败处理（第 70-71 行）｜错误处理体系与公共模块约定直接冲突**

- 触发条件：按设计卡"错误码统一使用标准库 net/http"+"严禁 panic"实现。
- 后果：需求文档阶段 1 已建成 `ErrorCode(40xxx/70xxx) + Throw panic + Recover 中间件` 体系，验收标准第一条就是返回 `{"code":40000,"message":"请求参数错误"}`。两套体系二选一，选 net/http 会破坏前端契约，且后续 8 个模块全部沿用 ErrorCode 体系，phase-01 会成为唯一例外。
- 缺失证据：设计卡未说明为何偏离需求文档的约定。
- 推荐修改：改回"业务校验 `common.Throw` panic、Recover 接住转统一 JSON、自定义错误码分段"，与需求一致。
- 待确认：是表述笔误，还是有真实理由要另起体系？

**DR-2｜阻塞｜事务/并发（第 24、67 行）｜"单点 refreshToken"不变量在当前设计下不成立**

- 触发条件：设备 1 登录后，设备 2 登录同一账号（此时只删 `user:refresh:{userID}`，未删 `refresh_token:{旧rt}`）；随后设备 1 拿旧 rt 调 `GET /refresh/token`。
- 后果：续签逻辑（参照需求 `refresh_token:{rt}`→查 userId→发新 access）**不校验该 rt 是否仍是 user:refresh 的当前值**，旧设备续签成功，不变量 3 被打破。此外设计卡验收场景写"续签时删除 old user:refresh 并换发"，意味着续签会轮换 rt——这与需求文档 `/auth/refresh` 只换 access、不轮换 rt 的行为**不一致**，属于未定义契约；若轮换，还引入并发续签竞态（页面并发多个请求同时 401，多个续签竞争会互相顶掉，可能把用户误登出）。
- 缺失证据：续签接口的完整逻辑（校验什么、轮换不轮换、如何防并发续签）。
- 推荐修改：三选一并写进设计卡——(a) 续签时原子校验 `refresh_token:{rt}` 的值 == `user:refresh:{userID}` 当前值（Lua 或两次 GET 比对）；(b) 踢号时同时删 `refresh_token:{旧rt}`；(c) 若轮换 rt，前端续签单飞（single-flight）+ 服务端留 30s 宽限期。推荐 (a)+(b)，实现最简单且闭合不变量。
- 待确认：续签到底轮不轮换 refreshToken？

### 重要问题

**DR-3｜重要｜API 契约（第 57-58 行）｜余额接口存在越权（IDOR）且鉴权方式未定义**

- 触发条件：已登录用户 A 调 `GET /balance/123`（别人的 userID）。
- 后果：设计卡写"获取**当前用户**余额"但路径参数是 `:userID`，若服务端不校验 token 中的 userID 与路径参数一致，任何登录用户可查任意用户余额与流水。设计卡通篇未写鉴权中间件方案（JWT 验签？还是需求文档暗示的 Redis 白名单查询？），权限校验无从谈起。
- 推荐修改：明确鉴权模式（推荐：JWT 验签 + Redis `access_token:{jwt}` 存在性校验，踢号才有即时性）；余额/明细接口校验 `token.userID == path.userID`。

**DR-4｜重要｜约束（第 34 行）｜MD5(salt+password) 的风险需显式接受**

- 触发条件：库泄露，攻击者拿 MD5 哈希离线爆破。
- 后果：MD5 在 GPU 上每秒数十亿次，固定 salt（需求文档为常量 `PasswordSalt="USER"`）可预计算彩虹表。这是您列为"约束"的选择（复刻课程），可以维持，但设计卡的风险区（第 6 行只写了唯一性/缓存/事务）应记录此已接受风险，否则评审无法区分"没意识到"与"主动接受"。

**DR-5｜重要｜核心流程（第 42 行）与约束（第 30、33 行）｜与需求文档的三个范围差异**

1. **注册事务范围**：需求文档注册事务是三步（用户+余额+**加机器人为好友**，落 friend/session/user_session 表），设计卡不变量 2 只写两步。若故意裁剪好友逻辑到 phase-04，需要在非目标里写明，否则实现时会对不上需求验收（"五表有数据"）。
2. **端口**：设计卡两处写 `:8001` 固定，需求文档全文为 `:8104`。是笔误还是有意变更？
3. **验证码一次性**：需求文档验证码登录成功后删除 key；设计卡第 41 行只写了 SETEX 300s 和发送限频，未写"用后即删"，也没写**校验失败次数限制**（6 位数字 300s 窗口内不限次尝试可被爆破）。

### 建议项（不阻塞）

- `GET /sendCaptcha`、`GET /refresh/token` 均为有副作用的写操作（写 Redis/发邮件/删旧 key），语义上应为 POST；`POST /info` 纯读取反而可用 GET。命名与需求文档不同（`/info` vs `/getUserInfo`、`/updatePwd` vs `/updatePassword`、`/refresh/token` vs `/auth/refresh`）无对错，但既然要改，建议连方法语义一起定。
- 第 65 行"事务使用 go-zero 自带的 sqlx 事务能力"不足以支撑跨 Model 事务——需求文档阶段 1 §3.7 已明确 go-zero Model 每次独立取连接，需用 `common/txctx.WithTransaction` 把 session 放进 context。照第 65 行写会做出"假事务"（各自提交）。
- WsServerLocator 读 etcd 的 realtime 节点，但 realtime 服务要到 phase-07 才存在。phase-01 联调登录时哈希环为空会怎样？需定义降级（返回空串/默认地址，登录不失败）。
- 唯一索引并发冲突时 MySQL 返回 duplicate key error，需映射为 `UserAlreadyExists` 而非 SystemError。
- 预签名 URL 有效期需求定为 30000s（约 8.3 小时），写权限泄漏窗口过长，建议缩短到 5-10 分钟。
- 第 92 行"验证码 300s 后正常可用"表述歧义，实际含义应为"300s 过期后可重新发送"。
- `balance_log` 未列字段、余额列类型未定（建议显式 BIGINT 存分）；第 6 行风险区提到 Kafka topic，但本卡 API 无 Kafka 依赖，属范围外监控项。

## ④ 方案比较

双 Token、一致性哈希、分存储、预签名直传四个核心取舍，作者的推理（第 76-87 行）成立，需求文档同构，**明确认可，不另提方案**。唯一值得给 B 的是密码哈希：A（您的选择）= MD5(salt+pwd)，成本为零、与课程一致；B = bcrypt/argon2id，多一个依赖，GPU 抗爆破强数个量级。前提区分：若本项目定位是学习复刻，维持 A 并记录已接受风险（DR-4）；若可能真实部署，B 是底线，且改动只在一处 `EncryptPassword` 函数，迁移代价极低。

## ⑥ 验证与复评入口

- 正常用例：注册→登录→续签→登出全链路，Redis 三个 key 的 TTL 与删除时序符合设计。
- 异常用例：过期/错误验证码、不存在账号登录、**旧 rt 在被踢后续签必须失败**（DR-2 的直接证伪用例）。
- 并发用例：10 并发同账号注册仅 1 条成功且返回 UserAlreadyExists 而非 500；同一 access 过期瞬间并发 5 次续签，明确期望行为（全成或恰一成）。
- 复评：修订后对照本清单逐条标注`已解决/维持原方案（附证据）/交由负责人`，按设计卡 §6 索引写入 `reviews/phase-01-用户模块.md`，评审者可做复评。
